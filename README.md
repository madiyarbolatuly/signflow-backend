# SignFlow — серверная часть

Электронное согласование и подписание служебных записок. Ключевая особенность:
согласующий принимает решение **по одноразовой ссылке, без регистрации**.

Проект форкнут от DocFlow/EDMS (`upstream` → `madiyarbolatuly/docedms`),
функциональность документооборота из него удалена. Техническое задание —
`SignFlow_TZ.docx` в рабочей папке.

## Запуск

```bash
cp .env.template .env      # заполнить JWT_SECRET_KEY и пароль базы
docker-compose up --build
```

Миграции применяются автоматически при старте контейнера `api`. Первичное
наполнение (администратор + три шаблона служебных записок):

```bash
docker-compose exec api python -m app.scripts.seed --admin-email admin@example.com
```

API: `http://localhost:8000/v1`, документация — `http://localhost:8000/docs`.

## Разработка без Docker

```bash
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m alembic upgrade head
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
```

Тесты идут на SQLite в памяти, база для них не нужна:

```bash
.venv/Scripts/python -m pytest -q
```

### Как устроен маршрут

Маршрут — последовательность **уровней**; шаги внутри уровня активируются
одновременно. Политика уровня определяет условие закрытия:

- `all` — решение должны принять все участники уровня;
- `any` — достаточно одного.

Последовательный маршрут — это цепочка уровней по одному шагу, отдельной
логики для него нет. Это решение позволило обойтись одной машиной состояний
вместо двух ветвей кода.

Пример запуска маршрута «руководитель, затем любой из двух кадровиков»:

```json
{
  "route": [
    {"policy": "all", "signers": [{"user_id": "01J..."}]},
    {"policy": "any", "signers": [
      {"email": "hr1@example.com"},
      {"email": "hr2@example.com"}
    ]}
  ]
}
```

### Решения, которые стоит знать перед правкой

- **Состояния — строки с CHECK-ограничением**, а не `Enum` из PostgreSQL:
  `ALTER TYPE ... ADD VALUE` не откатывается в транзакции, и каждое новое
  состояние ломало бы откат миграции. В EDMS с `DocStatus` это уже болит.
- **Транзакцией владеет зависимость** `get_async_session`: она фиксирует при
  успехе и откатывает при исключении. Сервисы и обработчики `commit()` не
  вызывают. В EDMS зависимость делала `flush()` без `commit()`, и часть
  изменений не доходила до базы.
- **Схему ставит только Alembic.** `metadata.create_all()` на старте, как в
  EDMS, не вызывается: именно из-за него там схема на разных площадках
  расходилась, а `migrations/versions/` остался пустым.
- **Почта уходит после фиксации транзакции**, через `BackgroundTasks`, и
  блокирующий `smtplib` вынесен в отдельный поток. Иначе недоступный SMTP
  занимает воркер до таймаута, а письмо могло бы уйти о событии, которое
  затем откатилось.
- **Погашенная ссылка не удаляет токен** — он часть доказательной базы.
  Нерабочей её делает состояние шага, которое проверяет публичный обработчик.
- **Просроченные ссылки помечает `expire_overdue()`**, а не читающий
  обработчик: исключение откатывает транзакцию, поэтому запись из обработчика
  всё равно не сохранилась бы. Функцию вызывает регламентное задание.

## Приёмочные испытания

Раздел 7 ТЗ, девять сценариев. Автоматизированы все девять.

Восемь идут на SQLite в памяти, база не нужна:

```bash
.venv/Scripts/python -m pytest -q
```

Испытание № 1 (миграции) — отдельно, в обе стороны:

```bash
.venv/Scripts/python -m alembic upgrade head
.venv/Scripts/python -m alembic downgrade base
```

Испытание № 7 — состязание на параллельном уровне — требует PostgreSQL:
проверяется блокировка строки маршрута, которой в SQLite нет.

```bash
docker run -d --name signflow-pg-test     -e POSTGRES_USER=signflow -e POSTGRES_PASSWORD=signflow     -e POSTGRES_DB=signflow -p 55432:5432 postgres:16

SIGNFLOW_TEST_PG=postgresql+asyncpg://signflow:signflow@127.0.0.1:55432/signflow     .venv/Scripts/python -m pytest -q
```

Без переменной окружения эти два теста пропускаются.

### О достоверности теста на состязание

Тест на гонку, который проходит и со сломанным механизмом, бесполезен, а
получить такой очень легко: `asyncio.gather` запускает две корутины, но между
точками ожидания они успевают выстроиться в очередь, и опасное окно просто не
наступает. Первая версия этих тестов была именно такой.

Поэтому в `tests/test_concurrency_pg.py` стоит шлюз, который удерживает обе
транзакции в точке перечитывания состояния уровня, и он включается только на
время гонки — иначе срабатывает ещё на подготовке данных и ломается по
таймауту. С отключённой `_supports_row_locks` хотя бы один из двух тестов
падает в каждом прогоне; с включённой оба стабильно зелёные. Поодиночке
каждый тест плавает, ценность имеет пара целиком.
